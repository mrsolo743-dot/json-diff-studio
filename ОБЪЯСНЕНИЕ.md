# Как устроен json-diff-studio

## Общая схема

```
JSON A, JSON B ──► diff()        ──► [Change…] ──► text / json / html
                └► make_patch()  ──► [op…]     ──► apply_patch() / verify
```

Обе функции обходят документы рекурсивно и используют одни и те же помощники: выравнивание массивов (`align`), выбор ключа (`choose_array_key`) и шаблоны путей (`PathMatcher`). JS-порт (`web/js/core.js`) повторяет код Python почти строка в строку.

## Пути (`paths.py`)

Путь — это кортеж токенов: строка (ключ объекта), число (индекс) или `KeyRef(index, key, value)`, то есть элемент, найденный по ключу. Благодаря `KeyRef` отчёт пишет `$.users[id=7].email`. Такой путь понятнее индекса и не «плывёт» при перестановках. При этом в JSON Pointer `KeyRef` превращается в обычный индекс.

Шаблоны игнорирования разбираются в список сегментов (`key`, `index`, `any`, `deep`, `keyref`). Сопоставление идёт рекурсивно с возвратом: сегмент `..` пробует «съесть» от нуля до всех оставшихся токенов. Шаблоны короткие, поэтому перебор дешёвый.

## Сравнение (`diff.py`)

- **Типы по правилам JSON:** `true` ≠ `1`, но `1` == `1.0`. В Python `True == 1`, поэтому равенство считает отдельная функция `strict_equal`, а не `==`.
- **Объекты:** ключи обходятся в отсортированном порядке. Так отчёт детерминирован и одинаков в Python и JS (в JS порядок ключей вида `"1"` отличается от порядка вставки).
- **Массивы, режим по умолчанию — LCS.** Каждый элемент превращается в каноническую строку (JSON с сортировкой ключей), затем строится наибольшая общая подпоследовательность. Между совпавшими элементами остаются «разрывы». В каждом разрыве первые `min(удалённых, добавленных)` элементов сравниваются попарно (рекурсивно), остальные считаются удалёнными или добавленными. Поэтому вставка в середину выглядит как одно `added`, а правка поля внутри объекта в массиве — как `changed` этого поля, а не замена объекта целиком.
- **Производительность:** общие начало и конец массивов отсекаются до DP. Если оставшаяся таблица больше 2 млн клеток, LCS не считается и элементы сравниваются по позициям. Это защита от квадратичного времени на огромных массивах.
- **Массивы по ключу.** Правило применяется, только если у *всех* элементов обоих массивов есть скалярный ключ и он уникален. Иначе используется LCS, а не неверный отчёт. Перестановки находятся через наибольшую возрастающую подпоследовательность (LIS) старых индексов: элементы вне LIS помечаются `moved`. Это минимальный набор «реально переставленных» элементов.
- **Мягкие настройки** (допуск, регистр, порядок) влияют только на отчёт.

## Патч (`patch.py`)

- Патч строится отдельным обходом и всегда **точный**: допуск и регистр на него не влияют. Так `apply(a, patch) == b` гарантировано (кроме путей из `--ignore`).
- **LCS-режим:** ведётся индекс `idx` в «рабочем» массиве, который по ходу операций превращается в B. Удаления не сдвигают `idx`, вставки и пары сдвигают его на 1. Поэтому каждая следующая операция использует правильный индекс с учётом предыдущих.
- **Режим по ключу:**
  1. Удаления выполняются с конца, чтобы индексы не сдвигались.
  2. Затем массив B проходится по порядку, и для каждой позиции нужный элемент ставится на место через `add` или `move`. Ведётся симуляция списка ключей, поэтому `from` и `path` у `move` всегда верны.
- **`apply_patch`** работает на глубокой копии, поэтому применение атомарное: при ошибке исходник не меняется.
  - Строго проверяются индексы (без ведущих нулей, `-` только для `add`).
  - Запрещён `move` внутрь самого себя.
  - `test` сравнивает значения по правилам JSON.
  - В JS ключ `__proto__` записывается через `defineProperty`: обычное присваивание поменяло бы прототип объекта.
- **Корректность проверяется свойством:** на сотнях случайных документов и мутаций `apply(a, make_patch(a, b)) == b`, с `test`-операциями и без, в обеих реализациях.

## Отчёты и CLI

- **HTML-отчёт** — один файл без внешних ресурсов. Данные вшиты как JSON, а `</` экранируется, чтобы значения вроде `</script>` не ломали страницу. Заголовок экранируется как HTML.
- **Коды выхода:** `diff` по умолчанию возвращает 0, а с `--exit-code` — 1 при различиях (как `diff`/`git diff`), удобно для CI. Ошибки ввода дают код 2 с понятным сообщением: строка и столбец для битого JSON, текст ошибки для плохого шаблона.

## Веб-песочница

- Чистые ES-модули без сборщика. `core.js` не зависит от DOM, поэтому его же тестирует `node:test`.
- `JSON.parse` в разных браузерах сообщает о позиции ошибки по-разному. Поэтому при ошибке текст проходит через маленький сканер `findJsonErrorOffset`, который находит смещение и переводит его в строку и столбец.
- `localStorage` используется только для удобства (последние данные и настройки), всегда внутри `try/catch`. Без хранилища всё работает.

## Общие фикстуры

`tools/gen_fixtures.py` прогоняет 20 показательных кейсов через Python и записывает ожидания в `fixtures/cases.json`. Эти же ожидания проверяют `tests/test_fixtures.py` и `web/tests/core.test.mjs`. Любое расхождение реализаций сразу видно в тестах.

## Что можно улучшить

- Трёхсторонний merge (`base`, `ours`, `theirs`) с поиском конфликтов.
- JSON Merge Patch (RFC 7396) как второй формат.
- Поддержка YAML и JSON5 на входе.
- Side-by-side просмотр с подсветкой прямо в тексте документов.
- Алгоритм Майерса O(ND) вместо табличного LCS для очень длинных массивов с небольшим числом изменений.
- Публикация в PyPI и npm, GitHub Action для `--exit-code` в CI.
